Hermanus event feed · design write-up

Magic Feed design

An event feed for travel planners. The first place is Hermanus, South Africa. Agents fill the feed and read it through one API.

Summary

A planner looks at the same place several times between the booking and the trip, often 6 to 18 months apart. The feed must hold events of every time shape: one date, a weekly market, a run of 81 shows, a season with months only, and an event that is likely but has no dates yet.

The feed works in three stages. An agent stores each source item unchanged as a scan. A second agent turns scans into events with times, labels and a confidence score. An event with a confidence of 0.8 or higher and approved labels goes to the feed. Other events go to a person for review, with the reason. A planner's agent then searches the feed by place, trip dates and traveller profile.

The first version uses one source, The Village NEWS events calendar. The API is Hono over SQLite. Plain Claude agents do the ingestion, the processing and the trip search by following skill files.

Data model

The core of the model is the split between what happens (Event) and when it happens (Time). One event has one or more times. Each time has a type and a precision, so the feed can store a date, a month or no date at all.

EntityPurposeKey fields
PlaceThe area that the feed covers.aliases such as Onrus, Sandbaai, Hemel-en-Aarde
SourceA site that the feed reads.kind, active
ScanOne raw item from a source, as fetched.raw, content_hash, state, event_id
EventWhat happens and who it suits.category, interests, suitability, confidence, confidence_reason, review_state
TimeWhen it happens.type, start, end, precision, rrule, exceptions, start_time
Event changeOne changed field.old_value, new_value, reason, actor, scan_id
TermOne allowed label value.status: approved or proposed

The API computes the status of an event for a given date: upcoming, running, finished, expected, cancelled or postponed. It does not store the status, so the same event shows a correct status on every visit.

Interface

The API is the only way to read or change the feed. GET / returns a guide that lists the calls for each task, and GET /openapi.json has the full schema.

Each search result lists the dates of the event inside the trip window, so an agent does not expand an rrule itself. Each 400 error lists every problem and the allowed values, so an agent can correct the request without reading the code. A person can see the same data at /feed.

Agent tasks

  • ingest-sources

    The agent fetches each active source and posts every item to POST /scans without changes. It does not filter. The API hashes each item. An item with the same content does not create a new scan, and the linked event gets a new last-checked date. A changed item becomes a new pending scan.

  • process-scans

    The agent reads the pending scans and decides for each one. It checks that the location is in the place, and that a traveller can go to the event. It looks for an existing event by name before it creates one. It merges repeated listings into one recurring event. It chooses labels from the vocabulary, sets a confidence, and states the fact that lowers the confidence.

  • find-events

    The agent maps the traveller's interests to vocabulary terms and searches the trip window. It runs a second search without the interests filter, so it can mention a large event that the traveller may want anyway. It lists expected events separately and shows ticket sale cutoffs first.
